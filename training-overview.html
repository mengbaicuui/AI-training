大模型训练方法概览

从「大一统预训练」到「面向业务的精调与对齐」，梳理一个可落地的大模型训练全景图。

1. 整体视角：大模型训练四个阶段

1.1 经典「3+1」流程

大语言模型从「通用能力」到「业务可用」通常经历四个阶段：

本课程更多聚焦在后面三个环节（SFT、对齐、压缩），这些都是数据工程人员可以参与、也最接近业务价值的阶段。

1.2 面向业务落地的三种典型路径

🧱

大多数企业不会从零训练基础模型，而是选择在通用基座（Qwen、Llama 等）上做 二次训练 + 压缩部署。本工作坊的重点也是：如何围绕这些环节做数据工程。

2. 预训练：你需要了解到什么程度？

2.1 预训练的目标与数据

预训练阶段的核心是：让模型在海量文本上学习「语言建模」任务，即预测下一个 token：

数学视角（简化）
// 给定前面所有 token，预测下一个 token 的概率
maximize  ∑ log P(tokent | token<t)

// 对数据工程的启示：
//  - 预训练数据越多、越干净，基础能力越强
//  - 预训练阶段关注“覆盖面”和“多样性”，不是具体任务

典型预训练数据包括：网络爬虫文本、书籍、代码、论坛对话等，规模通常是 TB 级，远超企业可单独构建的量级。

2.2 作为业务方/数据工程师，需要知道的边界

  • ✔ 预训练极其耗费资源，通常由大厂或基础模型团队承担
  • ✔ 你的工作更聚焦于：在预训练模型之上做增量数据工程
  • ✔ 需要知道预训练大致用过哪些公共语料，避免在下游数据中重复灌入无效信息
  • ✔ 明确：预训练不保证「对齐」，它只让模型会说话，会“胡思乱想”
⚠️
实际项目中，「预训练做不好」和「微调数据做不好」很难区分。从团队可控性的角度，更应该把精力放在后面的 SFT / 对齐 / 蒸馏 数据工程。

3. SFT：从基础模型到任务模型

3.1 SFT 的输入输出形式

SFT 是在预训练模型之上，使用「指令-回答」数据做监督学习。典型数据结构：

字段作用示例
instruction 告诉模型「要做什么任务」 请根据以下配置，生成一条 API 调用示例
input 任务相关的具体内容（可为空） 接口定义 JSON、表结构、业务参数等
output 我们期待模型输出的内容 一条合法的 curl 命令 / SQL / 对话回答

本工作坊的 《SFT 与 PEFT 的数据工程》 页面会详细展开如何构建这些数据。

3.2 SFT 解决了什么问题？

从“知道”到“按要求说出来”
预训练模型往往已经「知道」很多事实，但 SFT 教会它在特定任务中如何组织答案、遵守格式与角色设定。
输出可控性
通过大量示例告诉模型「该说什么、不该说什么」，例如：不要随意编造数据、不要输出敏感信息等。
快速适配领域语言
通过垂直领域 QA 样本，让模型熟悉汽车、金融、制造等专业术语与表达方式。

4. 对齐：从「会做题」到「行为符合预期」

4.1 RLHF / DPO 的核心思路

对齐阶段通常不再直接给出「标准答案」，而是给出偏好信息，让模型学会哪种回答更好：

方法训练数据直观理解
RLHF question + (answer, score) 或 (answer A, answer B, 人类偏好) 先训练一个「奖励模型」，再用强化学习调整语言模型
DPO question + (preferred answer, rejected answer) 直接最大化「好答案」相对于「差答案」的概率
🏷️
从数据工程视角看：对齐的关键是有高质量的「比较数据」——针对同一个问题，准备多种回答，并明确哪个更符合业务与安全要求。

4.2 对齐中的数据来源

  • 内部客服/机器人历史对话日志（需要做脱敏与清洗）
  • 标注团队针对常见问题给出的多版本回答与偏好选择
  • 通过大模型生成多个回答，再由人类选出更合适的一条（人机协同）
  • 安全/合规模块给出的「不允许输出」的负样本

5. 部署与压缩：从「好用」到「用得起」

5.1 为什么需要蒸馏、量化、剪枝？

一个效果很好的大模型，如果部署成本过高、延迟过大，在企业内往往是无法真正落地的。典型痛点：

  • 推理显存需求高，难以在现有 GPU 资源上大量并发部署
  • 单次响应延迟高，无法满足在线业务 SLA
  • 能耗与成本难以接受（尤其是 24×7 在线服务）

因此需要在保持尽可能多能力的前提下，通过 蒸馏 / 量化 / 剪枝 把模型变小、变快。下一节 《模型优化：蒸馏、量化、剪枝》 会重点展开。

5.2 对数据工程的整体要求

从大模型训练全流程看，数据工程的工作可以简单归纳为三类：

阶段数据类型数据工程重点
预训练 大规模通用文本 清洗、去重、多样性、合规（通常由基础团队负责）
SFT / 对齐 指令-回答 / 偏好数据 如何把企业文档/日志转成结构化训练数据
压缩（蒸馏等） 「教师-学生」训练对、推理日志 采样策略、难例挖掘、在线数据闭环

大模型训练方法流程与实践概览

从预训练到部署的完整技术链路，理解数据在各阶段的作用

训练全景：预训练 → 微调 → 对齐 → 部署

为什么需要分阶段训练？

大模型不是一步练成的。预训练学「通识」，微调与对齐学「听话、好用」，部署阶段则关注延迟与成本。每一阶段的数据形态、规模和工程要求都不同，数据工程正是串起这条链路的底座。

各阶段对比

阶段数据形态目标数据工程重点
预训练海量纯文本 / 代码语言建模、世界知识去重、质量过滤、长上下文
SFT指令-输入-输出三元组按指令回答、格式一致格式统一、多样性、标注质量
对齐（RLHF/DPO 等）偏好对、排序数据符合人类偏好、安全偏好标注、一致性、安全边界
推理 / 部署请求-响应流低延迟、高吞吐输入规范化、输出解析、监控

数据在各阶段的角色

数据决定模型天花板

同一套模型结构和算法，换一批数据，效果可能天差地别。预训练阶段关注规模与多样性；微调阶段关注「指令-答案」的准确与一致；对齐阶段关注人类偏好与安全边界。数据工程要针对不同阶段设计采集、清洗、存储与迭代流程。

PEFT：高效微调与数据需求

PEFT 是什么？

PEFT（Parameter-Efficient Fine-Tuning）指只更新少量参数的微调方式，如 LoRA、QLoRA、Adapter、Prefix Tuning 等。与「全量微调」相比，PEFT 省显存、省时间，且往往更不容易灾难性遗忘。

重要：SFT 和 PEFT 是不同维度——SFT 说的是「用什么数据」（监督指令数据），PEFT 说的是「怎么训」（只训少量参数）。两者搭配时，数据准备完全一致，都是指令-输入-输出格式。

LoRA 核心思想（与数据无关，属训练方式）

LoRA 用低秩矩阵 \(B \cdot A\) 近似权重更新 \(\Delta W\)，原始权重 \(W_0\) 冻结，只训 \(B、A\)。推理时可把 \(B\cdot A\) 合并进 \(W_0\)，无额外延迟。

📌
延伸学习：LoRA/QLoRA 原理、Rank 与 Alpha 配置、灾难性遗忘应对等，详见 《主流 PEFT 技术实战》（llm-finetune-course/peft.html）。
