SFT 与 PEFT 的数据工程

指令微调的定义与场景、数据构建全流程、LoRA/QLoRA 高效微调

1. SFT 定义和应用场景

什么是 SFT？

SFT（Supervised Fine-Tuning，监督微调）是在预训练大模型基础上，使用「指令-回答」结构化数据进行训练，让模型学会：

  • 遵循指令、理解任务要求
  • 按照期望的格式和风格输出
  • 最核心的是：学会指令遵循，把知识按照要求表达出来

为什么需要微调？

大模型在预训练阶段学习的是语言分布和常识知识，但实际任务往往需要更精确的指令与特定的输出格式。微调能够使预训练模型在特定任务的分布上进行训练，通过少量任务数据输入与反馈调整模型输出质量，进而在生成质量与可控性上获得更大提升。

2. 微调与预训练的区别

小互动：你觉得微调和预训练的主要区别在哪？

思考一下，从以下三个维度，哪个是最核心的区别？

三大维度对比

维度 预训练 微调（SFT） 有区别？
模型结构 Transformer Decoder Transformer Decoder ❌ 相同
Loss 函数 Next Token Prediction
▶ Next Token Prediction

细微差别：

预训练 所有 token 都算 loss
SFT 只对 output 部分算 loss

但本质还是同一个 Loss 函数，只是 mask 不同

 ❌ 基本相同
数据 海量纯文本（TB 级） 指令-回答结构化数据 ✅ 核心区别
🎯
结论：数据是最核心的区别。
预训练用海量纯文本学「语言规律」；SFT 用结构化的「指令-回答」数据教模型「如何按要求回答」。所以数据工程是 SFT 成功的关键。

3. Chat Template 机制

为什么需要 Chat Template？

不同模型在训练时使用不同的「对话模板」来区分角色（system / user / assistant），并告诉模型「哪部分是输入、哪部分是需要学习的输出」。

  • 区分 system / user / assistant 等角色边界
  • 训练时对 output 部分计算 loss，input 部分 mask 掉
  • 推理时按相同格式拼接，保证模型理解输入结构

4. 微调数据构建（核心重点）

下面 4.1～4.8 为流程介绍：从数据格式、来源、文档转 QA、合成数据、量级、清洗到管道与版本管理，建立整体认知。具体的文档预处理（PDF 解析、分块策略）见下一章。

4.1 数据格式

SFT 数据的核心结构是「指令-输入-输出」三元组：

字段说明示例
instruction任务描述/指令「请用一句话总结以下段落」
input具体内容（可为空）段落原文...
output期望的回答该段主要讨论了...
Alpaca 格式示例
{
  "instruction": "请将以下文本翻译成英文",
  "input": "人工智能正在改变世界",
  "output": "Artificial intelligence is changing the world."
}

4.2 如何获取数据？

来源方式优缺点
人工标注 领域专家编写 Q&A 对 ✅ 质量高   ❌ 成本高、速度慢
文档转 QA 从已有文档提取问答对 ✅ 利用存量资产   ❌ 需设计提问策略
合成数据 用大模型生成训练数据 ✅ 快速扩量   ❌ 质量需把控

4.3 从文档转为 QA 对

核心问题：谁来想问题？用什么策略提问？

策略做法适用场景
基于段落摘要 让模型针对每段内容生成「这段说了什么」类问题 知识问答
基于实体/术语 抽取关键实体，生成「XX 是什么」类问题 术语解释
基于业务场景 模拟用户真实会问的问题（「怎么办理」「多少钱」） 客服、咨询
多跳推理 需要结合多段信息才能回答的问题 复杂问答

4.4 合成数据的方式

用大模型（如 GPT-4、Qwen-Max）批量生成训练数据，常见方法：

方法原理参考
Self-Instruct 给几个种子示例，让模型生成更多类似指令 Stanford Alpaca
Evol-Instruct 对简单指令逐步「进化」为复杂指令 WizardLM
蒸馏 用大模型的输出作为小模型的训练标签 Alpaca、Vicuna
💡
合成数据注意事项：需要人工抽检质量、过滤低质量样本、避免模型「自我强化」错误模式。

4.5 数据量级：多少数据才够？

场景推荐数据量说明
风格调整 / 格式控制 几百 ~ 几千条 任务简单，少量高质量数据即可
垂域知识问答 1万 ~ 10万条 需覆盖领域知识点
复杂推理 / Agent 10万+ 条 多样性和难度梯度很重要
⚠️
质量 > 数量：1000 条高质量数据的效果可能好于 10000 条低质量数据。先保证质量，再扩充数量。

4.6 数据清洗

清洗项做法
去重基于 hash / embedding 相似度去除重复或近似样本
长度过滤过滤过短（无意义）或过长（超出模型上下文）的样本
质量打分用规则或小模型对样本质量打分，过滤低分样本
格式校验确保 JSON 格式正确、字段完整
敏感词/合规过滤敏感内容、确保符合业务合规要求

5. 具体的文档预处理方法

在「流程介绍」之后，落地到两件事：文档怎么进来（尤其是 PDF 的解析）、文档怎么切（分块策略）。前者重点介绍 VLM 处理 PDF，后者给出按场景的推荐策略与参数。

5.1 VLM 处理 PDF（重点）

PDF 是微调数据的重要来源，但原生是「像素/矢量」而非文本。要转为可分块、可生成 QA 的文本，需要版面分析 + OCR/文本抽取。视觉语言模型（VLM）与多模态文档解析工具能同时理解版面（标题、段落、表格、公式、图）并输出结构化文本。

  • MinerU（OpenDataLab）：多模态文档智能解析，PDF → Markdown/LaTeX/HTML。采用版面检测（Transformer 页面对象检测）→ 内容识别（CRNN+TrOCR、公式识别）→ 后处理三级架构，支持文本型 PDF 原生抽取与扫描版 109 种语言 OCR；新版 hybrid 后端融合 pipeline 与 VLM，降低解析幻觉。适合批量 PDF 转结构化文本后再做分块与 QA 生成。
  • Unstructured / LlamaParse：将 PDF 解析为 HTML 或 Markdown，表格整体保留为一个块，避免行列关系被切碎；适合财报、规格书等含大量表格的文档。
  • 通用思路：文本型 PDF 可优先用原生文本抽取 + 版面信息；扫描版或复杂版式用 VLM/OCR 管线；表格密集文档务必「整表一 chunk」或专用表格解析，再接入后续分块与 QA 流程。
ℹ️
与微调数据流水线衔接：PDF 经 MinerU/Unstructured 等解析为 Markdown 或结构化文本后，可交给 Easy Dataset 等工具做「文本分割 → 问题生成 → 答案构建」，得到 Alpaca/ShareGPT 格式的微调数据。

5.2 文档分块方法

解析得到的长文档需要分块（chunk）后再做检索或生成 QA。不同场景下应选用不同策略与参数，以保证语义完整、不切断句子/表格、兼顾检索精度与上下文长度。下表按场景给出推荐策略、建议参数与核心理由。

场景 推荐策略/工具 建议参数（Tokens / Overlap） 核心理由
通用文本
新闻、报告、文章		 递归字符切分
RecursiveCharacterTextSplitter		 500–1000 / 10–15% 首选默认方案。优先按段落（\n\n）切，保证语义尽可能完整，不把一句话切断。
结构化文档
Markdown、Wiki		 按标题切分
MarkdownHeaderTextSplitter		 按 Header 层级 / 0 保留层级元数据。将 H1/H2 作为元数据注入内容，防止切片丢失「属于哪一章」的信息。
代码文件
Python、JS、Go		 语言结构切分
PythonCodeTextSplitter 等		 800–1500 / 0 保持逻辑完整性。按类/函数边界切，不会把一条 if 语句劈成两半。
包含大量表格
财报、规格书		 HTML/Markdown 转换
Unstructured / LlamaParse		 表格整体作为一个块 表格绝不能切碎。整张 <table> 解析为 Markdown/HTML 作为独立 Chunk，否则行列关系全毁。
高精度检索
法律条款、合规		 父子索引
ParentDocumentRetriever		 父: 2000 / 子: 200 搜得准、读得全。用「子块」做向量匹配（极灵敏），给 LLM 喂「父块」（上下文完整）。
话题跳跃性强
会议纪要、聊天记录		 语义切分
SemanticChunker		 基于语义阈值（Percentile） 按意思切、不按字数切。用 Embedding 判断话题何时结束，解决「上一句谈工资、下一句谈天气」混在一块的问题。
模型窗口极小
本地小模型		 固定大小切分
TokenTextSplitter		 256–512 / 20% 硬约束。显存受限或 Embedding 模型只支持 512 token 时使用。
✅
选型建议：先看文档类型（通用/结构化/代码/表格/多话题/小窗口），再选对应策略；参数可按数据抽样调试，优先保证「不切断语义单元」再调 chunk 大小与 overlap。

LoRA 核心思想

LoRA（Low-Rank Adaptation）通过低秩分解来近似权重更新：原始权重 W₀ 保持冻结，只训练两个小矩阵 B 和 A。

  • 原始权重 W₀ 保持冻结，不参与梯度更新
  • 只训练低秩矩阵 B 和 A，参数量大幅减少
  • 推理时可将 BA 合并到 W₀，无额外推理延迟

LoRA 参数配置

参数含义推荐值说明
r (Rank)低秩矩阵的秩8 / 16 / 32领域差异越大，Rank 越高
lora_alpha缩放因子= Rank 或 2×Rank实际缩放 = alpha / r
target_modules应用 LoRA 的层q_proj, v_proj可扩展到 k, o, gate 等
lora_dropoutDropout 比例0.05 ~ 0.1防止过拟合
Python - PEFT LoRA 配置示例
from peft import LoraConfig, get_peft_model

peft_config = LoraConfig(
    r=16,                        # Rank
    lora_alpha=32,                # Alpha
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)

model = get_peft_model(base_model, peft_config)
model.print_trainable_parameters()
# trainable params: 4,194,304 || all params: 6,738,415,616 || trainable%: 0.0622%

QLoRA：更省显存的方案

QLoRA 在 LoRA 基础上引入 4-bit 量化（NF4），使得在消费级 GPU 上微调大模型成为可能。

特性LoRAQLoRA
基础模型精度FP16 / BF16NF4 (4-bit)
7B 模型显存~16GB~6GB
训练速度较快略慢（需反量化）
适用场景显存充足显存受限（消费级 GPU）

小互动：为什么不推荐 Adapter / Prefix-Tuning / P-Tuning v2？

这些方法也是参数高效微调，但为什么实践中大家更倾向于用 LoRA？想一想它们可能有什么问题。

  • Adapter Tuning：增加了模型层数，引入了额外的推理延迟
  • Prefix-Tuning：难于训练，且预留给 Prompt 的序列挤占了下游任务的输入序列空间，影响模型性能
  • P-Tuning v2：很容易导致旧知识遗忘，微调之后的模型在之前的问题上表现明显变差
💡
LoRA 的优势：原始权重完全冻结（抗遗忘）、推理时可合并（无延迟）、不挤占序列空间。这就是为什么 LoRA/QLoRA 成为主流选择。
🏆
结论：综合考虑效果、显存和抗遗忘能力，LoRA / QLoRA 是目前最主流的微调选择。它在多个 benchmark 上证明，仅用 0.1% 的可训练参数即可达到接近全量微调的效果。
